## 0. 阅读键：层级与推进规则

需求可以列得很多，但**实现分步推进**（[D20](DECISIONS.md#d20--分阶段推进主线先行)）。本文各表的「层级」列取下面三个值之一：

| 层级 | 含义 | 对应阶段 |
|---|---|---|
| **主线** | 推理全链路诊断（性能 + 精度），在腾昇 + NVIDIA 上成立。**当前阶段只做这一层** | S1 → P0 → P1 → P2 → P4 |
| **扩展** | 主线完成后依次推进。主线阶段对它们的义务只有"不阻碍"，即不做冲突的假设，但不预先实现 | P5 规模化 → P6 第二家厂商 → P3 故障/在线/长稳 |
| **暂不做** | 当前范围之外，唯一出处是 [D21](DECISIONS.md#d21--范围边界暂不做与不做清单)；重新打开需用户裁决 | — |

新出现的需求先登记进 [§6](#6-需求池参考文档补充) 并标层级，不直接进入当前阶段。

## 2. 协同需求（v2 的数据被其他模块消费）

v2 不实现这些模块，但其事件与分析结果是它们的输入。**设计必须保证这些消费方能直接使用 v2 的产物，而无需再跑一遍采集。**

| ID | 消费方需求 | v2 提供 | 对设计的约束 | 层级 |
|---|---|---|---|---|
| R1 | 500 模型计算图解析：模型—算子映射、动态 Shape、数据类型 | Tier 0 下 dispatch 探针产出的 `op` + `sig` 即模型—算子映射 | `sig` 必须完整记录 shape/dtype（不能像 v1 那样每算子截断 32 条） | 主线 |
| R47 | 算子支持度扫描：缺失、回退与风险识别 | `route` 事件的 `decision/reason` 聚合 | 回退原因必须是枚举，不是自由文本 | 主线 |
| R18 / R22 | 后端映射与可控回退；算子级/实现级/芯片级三级回退；多芯片兼容性矩阵 | 跨 run（跨厂商）的 op×sig×route 矩阵 | 事件中区分"未注册""策略排除""运行时异常回退"三类 | 主线（单厂商）；扩展（多厂商矩阵，P6） |
| R37 | 能力矩阵驱动选算（依据形状、精度、性能数据选实现） | 按 sig 的耗时与数值误差表 | op 级精度与性能必须能按同一 `sig` join | 主线 |
| R45 | 编译缓存与回退治理 | `compile` 事件的缓存命中/失效 | 记录编译 key 与后端版本 | 主线 |
| R86 / R88 | A100 统一基线；跨芯片一致性分析（中间结果、算子支持、回退率、瓶颈） | seal 模式 + oracle 差分 + 跨 run 比较视图 | A100 与国产芯片使用**同一份** schema 与探针代码 | 主线 |
| R89 | 自动报告与验收归档：单模型记录和批量汇总 | campaign 索引 + 单 run 报告 | manifest 必须自带环境、配置、身份与完整性状态 | 主线（单 run 报告）；扩展（批量汇总，P5） |
| R106–R108 | 算子/运行时/编译问题反哺：问题复现和回归验证 | seal 模式的可复现 run；问题清单携带复现所需最小信息（sig、route、输入引用） | 导出清单能指回原始 run 与事件 | 扩展（P5） |
| R77–R79 | 统一观测（资源水位、作业监控、告警与自动恢复，调度层负责） | counter / health 事件流可被尾读 | 在线通道协议稳定，见 [08 §3](08-online-and-fault.md) | 扩展（P3） |

## 4. 从 v1 继承且仍然有效的需求

以下需求来自 v1 `inference/plan.md`，经核对在 v2 中继续有效，但实现方式改变：

| v1 需求 | v2 中的形态 |
|---|---|
| FlagGems / FlagTree / FlagCX 的 off/on/both 开关，一次只允许一个 `both` | seal 模式下的对照实验矩阵维度，见 [09 §3](09-cli-and-campaign.md) |
| FlagGems 不可用算子清单（v1 的 preview 阶段） | 变成 `route` 分析器的产物：一次 run 即可得到"哪些算子在 FlagGems 下失败及原因"，不再需要独立的搜索流程。若需要逐个隔离验证，作为分析器驱动的二次 run，见 [07 §3.2](07-analyzers-and-reports.md) |
| 精度与性能分开输出 | **采集可以同时，分析与报告分开**。但 tensor 探针会扰动计时，因此预设（preset）层面默认分开采集，见 [05 §3](05-probes-and-vendors.md) |
| 精度不设阈值，客观报告 | **分析器**保持不设阈值：只输出指标，不给 pass/fail。参考文档要求的"自定义容差、异常算子判定、门禁"作为分析器**之上**的独立判定层，属扩展（[§6](#6-需求池参考文档补充)），不进入分析器 |
| 每个指标必须写明来源/API（指标来源矩阵） | 每个探针与分析器在 registry 中声明来源；指标来源矩阵由 registry 生成，见 [07 §5](07-analyzers-and-reports.md) |
| 默认精简保留，失败/异常保留现场 | store 的保留策略，见 [03 §7](03-event-schema.md) |
| 关联缺失时标 partial，不伪造 | 关联状态枚举 `linked/ambiguous/unlinked`，见 [04 §2](04-correlation.md) |
| 模型权重由用户下载，离线加载 | 保持 |

## 5. 非功能需求

| 编号 | 要求 | 验证方式 |
|---|---|---|
| N1 开销可控 | 每个探针声明开销等级；性能预设的端到端开销须实测并写入报告 | P1/P2 验收中的开销对照 |
| N2 崩溃可用 | 进程被杀后，已落盘的事件仍可读，manifest 能识别截断 | P0 验收：kill -9 后读取 |

| N4 可复现 | seal 模式下同一输入、同一环境重复运行，身份一致；差异必须可解释 | P4 验收 |
| N5 规模 | 500 模型 × 5 厂商 × 若干组件开关的 run 可索引、可检索、可断点续跑 | P5 验收 |
| N6 可审计 | 每个结论能追溯到原始事件；关联率、采样空洞、丢弃数量对用户可见 | 每个分析器输出 coverage 字段 |
