# 训练发车参考约定（launcher conventions）

多卡训练验证的批量发车脚本（docker run + torchrun）反复踩到的坑，沉淀为约定。
写新发车脚本前逐条对照；flagprof 自身的平台适配见 `docs/training/v2.md`。

## 1. 返回码约定（防假绿）

- `docker run` 的退出码**不是**训练退出码：payload 以 `echo $? > ...returncode`
  结尾时，docker/bash 层面看到的永远是 echo 的 0。
- **判定只认容器内进程写的 returncode 文件**（容器以 root 或指定 uid 落到挂载卷）。
  批量编排器的 status 行会记录 docker 层 rc，仅作存活信号。
- 容器内执行的 payload 必须 `exit $rc` 把训练 rc 传给 docker 层。

## 2. 设备与 rank（节点数 = rank 数）

- torchrun `--nproc-per-node=N` 要求容器内恰好可见 N 个设备节点：挂 3 个节点跑
  4 rank 会在 `set_device` 报 `invalid device ordinal`。
- 单进程（无 --ddp）显式 `--device cuda:0`：裸 `cuda` 在部分 torch 版本
  （2.9）被 set_device 拒绝，2.10 容忍——统一写带索引形态，跨版本安全。
- 多卡容器内 cuda:N 的设备顺序由挂载的节点枚举决定（P800/xpu 实测枚举序=节点
  号序，与 SMI 号可能错位）；需要卡身份时先跑 inventory/枚举对照，不要凭 SMI
  号猜。

## 3. 观察态（FLAGPROF_TRAIN_OBSERVE）约定

框架侧已内置三项客户便利（`flagprof/training/__main__.py::observation_start`）：

- 昆仑芯 P800 识别为 `kunlunxin`（内置训练入口按设备型号自动识别，外部框架可显式设 `FLAGPROF_TRAIN_OBSERVE_VENDOR=kunlunxin`）。内置入口在导入 torch 前为已识别的 P800 设置 `XPU_ENABLE_PROFILER_TRACING=1` 和 `XPU_CUPTI_ENABLE_DEVICE`。外部训练框架须在各 worker 导入 torch 前设置这两项，后者取该进程逻辑卡号（torchrun 下通常为 `LOCAL_RANK`）。物理身份由 `xpu-smi` 查询，也可挂载[宿主查询清单](../kunlunxin/inference-v2.md)。在 P800 上强指 `thead` 会在官方采集器启动时因缺 XPU profiler 门失败并如实记录，不应作为观察会话。
- 平头哥 PPU 使用 `thead`。其 `FLAGPROF_THEAD_IDENTITY` 缺省时，框架在每个 rank 的 run 目录写入 `identity-autogenerated.json`，记录可见设备名、逻辑序号和 UUID。物理卡号、设备节点与驱动版本需要独立的宿主机查询。
- 监控（`FLAGPROF_TRAIN_MONITOR=on`）的设备遥测：PPU 容器需挂载主机 `/usr/lib64/libnvidia-ml.so`（或设 `FLAGPROF_TELEMETRY_LIBRARY`）；P800 用镜像内 triton 包的兼容库，无需挂载。换机/换镜像先跑 `python3 -B -S -m flagprof telemetry check --vendor thead|kunlunxin`，失败会列出全部候选路径与原因。
- attach 失败时，store 内 producer.json 的真实错误会**冒泡到训练 stderr**
  （不再只报空错误列表）。

本节实机验证使用本地持久卷 ext4/XFS。0.3.0 将采集检查点放在 Store 所在卷，使用其他挂载时需验证文件锁、原子发布及中断恢复。观察容器和生成 identity 的环境应具有相同的设备枚举。

## 4. 容器与文件（交叉写）

- 编排器与容器对同一目录交叉写时，注意容器进程 uid（--cap-drop=ALL 会丢
  CAP_DAC_OVERRIDE，root 也只保有属主内的写权）。解法优先级：同一 uid 跑容器
  `--user` > 目录 777 + 宿主 umask 000 > 后台 chmod 循环（最后手段）。
- `setsid nohup ... > log 2>&1 < /dev/null &` 的 log 目标目录必须先建。
- 密闭（read-only）容器内挂载点父目录不可写，bind mount 的目标目录要把**父链**
  挂出来或预置于镜像。

## 5. 集合通信（XCCL/NCCL 系）

- broadcast 的非 root rank 必须提供**与 root 同尺寸**的 buffer，0 元素张量会
  挂死整个会话。
- reduce_scatter/all_gather 的输入输出列表**预建**在计时区外（clone/构造会污染
  计时）。
- 延迟测量统一"完成 API 含 synchronize"的墙钟口径（CLOCK_MONOTONIC），与
  toolkit native_bench 同基准。

## 6. git/传输

- Windows→Linux 传文件先查 CRLF（`grep -c $'\r'`），脚本带 CR 会在远端
  bash/Python 解析错位。
- git bundle 增量传输用 ref 名（裸 SHA 拒建）；目标分支已检出时 fetch 走
  FETCH_HEAD + `merge --ff-only`。
- push 前 `ls-remote` 核对目标 ref；新工作只推同名新分支。

## 7. 多租户宿主共存（共享机器）

- `torchrun --standalone` 的 rendezvous 端口可能与同宿主其他训练容器冲突：
  `DistStoreError: wait timeout ... keys: /default_pg/.../flagcx_dev` 优先怀疑
  端口/通道撞车，而不是设备问题。错开方式：`--standalone --master-port=<自由端口>`。
- 同宿主租户进程占用单卡（xpu-smi 可见）不必然阻塞其他卡的训练——先按卡号核对
  挂载清单，再判断是否真的冲突。
- 附带产物：多卡长跑的稳态步时与 samples/s 从 steps[].synchronized_step_ns 直取
  （剔除首步冷启动），作为吞吐基线口径。

## 8. 入口形态：统一走 training/run.py

`training/run.py` 是文档化的训练 v2 入口（自动加入 inference 包路径，免设
PYTHONPATH），与 `python -m flagprof.training` 逐位等价——同参对照 sha 一致
（P800 cuda:0 实测 ENTRY-PARITY-MATCH，runpy/module 双形态 f2a02f66…）。
批量发车统一用脚本路径形态，命令外观从 training/ 出发：

```
python training/run.py --task ctr --ctr-arch din --package ... --device cuda:0 ...
torchrun --standalone --nproc-per-node=4 training/run.py --task rerank ... --ddp ...
```

torchrun 以脚本路径启动时各 worker 从头执行 run.py，sys.path 注入同样生效。
历史上以 `-m flagprof.training` 跑出的证据命令保持原样（记录当时真实形态）。

## 9. Ascend 910C 发车约定

本节仅声明 **910C 实机验证**（Atlas 800T A3，8 卡 × 每卡 2 chip = 16 个
device；npu1-11 / npu1-27，CANN 9.x，flagrt `ascend-operator-runtime`
torch2.10 镜像）。其他 Ascend 型号未验证，不做推断。

- **容器形态**（照 `base/configs/ascend910_cann9_local.yaml`）：`--privileged` +
  `--network=host`（部分宿主无 docker0，bridge 不可用）+ 挂载
  `/usr/local/dcmi`、`/usr/local/Ascend/driver`、`/usr/local/Ascend/firmware`、
  `/usr/local/Ascend/version.info`、`/usr/local/bin/npu-smi`、
  `/etc/ascend_install.info` + 每卡 `--device=/dev/davinciN` +
  `--device=/dev/davinci_manager --device=/dev/devmm_svm --device=/dev/hisi_hdc`
- **CANN 版本对齐**：镜像把工具链放在 `/usr/local/Ascend/cann-9.0.0`。宿主
  CANN 可能是 8.5/9.1/9.2——把宿主对应版本目录**挂到该路径别名**即可（9.x 线
  向上兼容实测通过：cann-9.1.0 → /usr/local/Ascend/cann-9.0.0）。镜像内
  torch_npu 依赖宿主 driver/HAL 库，driver 挂载不可省。
- **设备计数**：npu-smi 显示 NPU 行数是卡数（每卡 2 chip）；torch 视角
  `torch.npu.device_count() = 卡数×2`。`--device npu:N` 的 N 是 chip 序号
  （npu:0/1 同卡两 chip）。
- **DDP**：`--ddp --backend hccl --device npu`（hccl 已入 choices；npu+nccl 会
  给出明确报错）。每 rank 自动绑定 `npu:local_rank`（早前版本会让所有 rank 绑
  npu:0 导致 HCCL ranktable 冲突——已修复）。
- **HCCL 端口**：同宿主有其他 HCCL 进程（租户容器）时可能报
  `Communication_Error_Bind_IP_Port(EI0020)`；可先试
  `-e HCCL_IF_BASE_PORT=<高位端口>`、`-e HCCL_SOCKET_IFNAME=<网卡>`，仍失败则
  等租户释放（环境级，非框架可解）。
- **观察态**：只设 `FLAGPROF_TRAIN_OBSERVE=<store>` 即可——vendor 按设备自动
  识别（npu → 内置 ascend session，torch_npu.profiler），无需手工指定。
- **checkpoint/resume**：npu 设备的 RNG 状态已支持（save/restore）。
- **位精确性注意**：910C 平台同一命令逐跑 final sha 可能不同（控制实验证实），
  sha 级"零漂移"判据在 Ascend 不适用；观察不扰协议需以行为级证据论证。
- **已知架构限制（dien，厂商算子规格）**：CTR `dien` 的 GRU 在 910C 上映射到
  融合算子 `DynamicGRUV2`，该算子**仅支持 FP16**（CANN 9.0/9.1/9.2 一致，
  报错 `Unsupported_Operator ... DT_FLOAT ... is not supported`），因此 FP32
  训练不被支持。本框架不通过静默换 dtype 规避——如实记录为厂商算子规格缺口，
  交算子团队评估（其余 13 个 CTR 架构不受影响）。另有已修复的潜在数据依赖
  bug：`pad_packed_sequence(total_length=...)` 在"批内最长序列 < history
  宽度"时形状报错（各平台通病），现已改为手动 pad 并加回归测试。

## 10. FlagScale 检索训练集成（适配器）

`inference/tools/flagscale_adapter.py`：外部训练循环（FlagScale/Megatron/FSDP2
风格，非 flagprof 引擎）挂运行时层的最小适配器，约 40 行、不改训练语义：

```python
from flagscale_adapter import ObservationSession
obs = ObservationSession()     # 读 FLAGPROF_TRAIN_OBSERVE；未设置则完全 no-op
with obs:                      # attach 官方 profiler + 通信探针 + 进程内 finalize
    for step in range(steps):
        with obs.phase('data', step=step):      batch = next(loader)
        with obs.phase('forward', step=step):   loss = loss_fn(model(**batch))
        with obs.phase('backward', step=step):  loss.backward()
        with obs.phase('optimizer', step=step): opt.step(); opt.zero_grad()
        with obs.phase('step', step=step):      pass
```

- vendor 自动识别（npu→ascend、PPU→thead、其余 NVIDIA→nvidia）；thead 身份
  文件缺失时自动生成（torch 真实 UUID）。
- **FSDP2 funcol 通路可见**（all-gather/reduce-scatter 逐调用入账）；传统 DDP 的
  C++ Reducer 不可见（已知边界）；Megatron p2p 入口已覆盖。
- 验证（`inference/tools/flagscale_demo.py`，thead 2 卡 FSDP2 两步）：
  双 rank `allgather 2 + reducescatter 2`、五相 ×2、manifest complete。
- 用法：训练脚本 `FLAGPROF_TRAIN_OBSERVE=<store> torchrun …` 即产 store，供
  comm-report（通信/计算分列、按 rank、等待-带宽、相段占比）直接消费。

## 11. FlagScale 真实集成（已实跑）

`inference/tools/flagscale_integration/` 提供在 FlagScale
`flagscale/train/train_retrieval.py` 上接入观察采集的完整工件
（patch + standalone 配置 + 数据生成脚本 + 复现命令）。PPU 双卡实跑结果：
train_loss 0.116918 / validation 0.000107；store 1.6 GB complete；
`comm={'model/allreduce': 2}`（评测归约；DDP 梯度 Reducer 按设计不可见）、
`phases={data:28, forward:27, backward:27, optimizer:27, step:27}`；
开/关采集两跑 `model.safetensors` sha256 逐字节相同。
