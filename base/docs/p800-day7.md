## Run

From the FlagPerf root, replace example card 5 with an authorized idle card.
SMI physical indices are not device minors; use UUID-joined bindings. Cards
1/2 remain excluded until their recorded health issues are resolved.

```bash
python3 -B base/run.py benchmark run --case computation-FP32:P800 \
  --config base/configs/kunlunxin_p800_xpytorch29.yaml \
  --physical-device-ids 5 --nproc-per-node 1 --timeout 300 \
  --allow-candidate-runtime --dry-run

sudo -v  # interactively, same terminal; no credential in scripts
python3 -B base/run.py benchmark run --case computation-FP32:P800 \
  --config base/configs/kunlunxin_p800_xpytorch29.yaml \
  --physical-device-ids 5 --nproc-per-node 1 --timeout 300 \
  --allow-candidate-runtime --monitor on --privilege-command 'sudo -n' \
  --reservation-reference ACTUAL_AUTHORIZATION_REFERENCE \
  --reservation-end END_TIME_WITH_TIMEZONE \
  --result-dir base/result/NEW_UNIQUE_ATTEMPT
```

Transfer overrides are
`base/benchmarks/interconnect-{h2d,d2h}/kunlunxin/P800/case_config.measured-{pageable,pinned}-{blocking,nonblocking}.yaml`.
Pass the matching file with `--case-config`. Capacity alone requires
`--allow-high-risk-case`. Timeout is 30–180 seconds for preflight and 30–600
for performance.

Communication uses the exact intraserver case, two authorized physical IDs and
`--nproc-per-node 2`. The existing `flagperf-p800-internal` Docker bridge must
be internal-only. Inspect it with
`sudo docker network inspect flagperf-p800-internal`. The provider does not
create host networks; a missing bridge is a prerequisite failure, not proof of
unsupported BKCL. Do not remove this shared prerequisite during per-run cleanup.

The independent P800 Toolkit path is selected with `python3 -B base/run.py toolkit run`
and keeps a separate measurement contract. Its default GEMM scope is matrix 8192 with
five independent repeats and a 600-second command timeout. P2P bandwidth keeps the
historical 32 MiB default for compatibility; use `--p2p-payload-bytes 268435456` for
a 256 MiB comparison plan. This option has passed static and contract tests, but a
256 MiB hardware result still requires an idle, healthy, authorized pair and five-run
evidence. Toolkit P2P is single-process `xpu_memcpy_peer`; it must not be divided
directly into the Base FlagCX/BKCL multi-rank result.

## Qualification and limits

The Day 7 plan freezes case, config hash, card set, repeats and evidence path.
Do not mix UUIDs, code hashes, payloads or request modes within five-run groups.
Use sample standard deviation (ddof=1); CV above 5% is unstable. Keep all samples.

`base/qualification.py DIR1 DIR2 DIR3 DIR4 DIR5 --output NEW_STATS.json` validates
eligible single-rank computation, transfer and memory-bandwidth groups. It does
not accept capacity or two-rank groups. Day 7 communication statistics separately
validate both ranks and use the lower rank bandwidth, never their sum.

Monitor-off is for alternating on/off comparisons only; it does not replace
monitored qualification. Paired differences include shared-host variation.
Capacity is a search, not a throughput loop; document its short observation
window separately.

The XPULink/PCIe bandwidth discrepancy remains a vendor question. Six versus
twelve observed rings alone do not prove a hardware maximum or causal model.
Day 7 corrects synchronization to the active verified rank. Old Day 6 records are
unchanged; new-code results are kept separate. No driver, firmware, BKCL library
or other tenant's workload is changed.

The MPI provider and driver accept 2–8 ranks, but the delivered hardware evidence is
limited to the two-rank path. Eight-card execution still requires an idle, healthy,
authorized resource window plus independent correctness, monitoring, cleanup and
five-run qualification evidence; two-rank results must not be extrapolated.
