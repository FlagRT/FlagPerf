## 结论

代码和证据框架已经可以收尾交付，但 Base 不能写成“全部硬件验收通过”。单卡卡5的计算、传输、设备内存带宽和容量实测已完成；两卡 MPI/P2P 五次结果通过数值与正确性审计，但由于卡0存在外部占用，只能是 exploratory。七卡 AllReduce 的测量和正确性通过，八卡正式验收被卡1的设备执行通路阻塞：2026-09-30 19:43:29 内核日志记录 KL_XID_KERNEL_EXCEPTION、reason[29] task timeout，且卡1在初次 device checksum 后停滞。不能用七卡结果外推八卡。

Toolkit 三个新 run 的证据审计全部通过，但实验状态保持 partial：厂商阈值 diagnosis 不支持，集成 smoke 的监控也不是完整资格窗口。D2D 已拆成两个有明确语义的指标，不能把约 10 GB/s 的 runtime memcpy 和约 2.09 TB/s 的 XBLAS Scopy read+write 混称为同一条 HBM 带宽。

## Toolkit 与 Base/Ascend 的口径核对

新 Toolkit 单卡 run 的 70 个原生指标和 15 个容量字段、P2P run 的 15 个指标、集成 run 的 95 个原生指标和 6 个容量字段，均通过独立审计器的 hash、命令、设备绑定、payload、correctness coverage、公式、monitor raw window 和重复次数检查。Toolkit sustained GEMM 中位数约为 FP32 118.53、FP16 269.25、BF16 118.8、INT8 465.7；INT8 比 Base 503.5 TOPS 低约 7.5%，但输出类型和 API 不同（Toolkit 为 XBLAS fc_fusion、FP32 输出；Base 为 xtorch_ops.gemm_I8_I8_bf16_nt），不能归因成单一硬件性能退化。

Toolkit D2D 的 runtime memcpy 约 9.8–10.0 GB/s，独立 XBLAS Scopy kernel 为约 2090.9–2095.0 GB/s，后者按两份 payload 计算 read+write。Ascend 参考包的 DMI 数值保留厂商原始口径，不对其再乘二；两者是不同 API/算法路径，不能直接排名。Ascend 参考还明确区分 measurement、monitoring、diagnosis 和 final status，P800 已按同样层次保留 diagnosis_status=not-supported。

## 已修复的代码问题

- provider 顶层导入改为 base.benchmarks.day6_contract，修复干净容器 ModuleNotFoundError。
- AllReduce 计时输入改为 world_size-1 与 -1 的零和系数，覆盖 2–8 ranks，避免八卡长循环数值漂移。
- capacity 释放门禁改为统一字节单位，清除最后一个 tensor 引用，验收器核对 held trail、释放后字节和 95% 恢复门槛。
- Day6 验收器不再只相信顶层 passed，强制检查 memory/MPI/P2P/capacity 的完整 correctness checks 和监控范围。
- Toolkit D2D 增加独立 kernel 模式；报告、公式和样本图按 payload/read+write 区分。P2P payload 参数、重复数和执行目标数进入静态计划。
- qualification 聚合改为逐 run 取最慢 rank，不相加多卡带宽；共享卡或不可纠正 ECC 自动降为 exploratory/not-qualified。
